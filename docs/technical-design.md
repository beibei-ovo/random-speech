# 随机演讲训练器 · MVP 技术方案

版本：v0.2。日期：2026-09-15。状态：技术路线已确定，语音转写服务采用用户配置的 ASR 或多模态音频接口；新增能力按下文设计推进。

产品依据：[MVP 产品设计](./product-design.md)。本文确定实现边界与关键技术决策，不代表功能已经开发或通过验收。

## 1. 已确定的方向与实施假设

- **已确定**：使用 Electron 桌面应用，支持真正的跨应用悬浮窗口。该决定补充产品文档中尚未确定的平台与悬浮方案。
- **实施假设**：首版优先 Windows 10/11 x64；macOS、Linux、ARM64 不列入首轮验收。最低系统版本还需与最终锁定的 Electron 版本核对。
- **数据策略**：无需注册，单设备使用；训练记录和音频保存在本地，转写与反馈使用云端服务。
- **服务选择**：用户分别配置语音转写与演讲评价服务。转写支持专用 ASR 或支持音频输入的大模型；应用按已支持的接口协议适配，不以模型架构限制选择，也不承诺任意 API 都能直接接入。
- **范围**：覆盖抽题、10 分钟查资料、5 分钟整理、2 分钟录音、反馈、同题重讲和历史管理。
- **首版不做**：账号、跨设备同步、自动搜索、视频、实时语音教练、本地大模型、语音唤醒、进步评分和自动更新。
- **仍需验证**：中文语音识别与模型供应商、服务留存政策和成本，以及正式分发前的密钥与签名方案。

## 2. 技术栈

| 层次 | 选择 | 用途与取舍 |
| --- | --- | --- |
| 桌面运行时 | Electron | 管理主窗口、置顶悬浮窗、托盘和系统事件；接受其安装体积与内存成本 |
| 语言与构建 | TypeScript、electron-vite、npm | 统一主进程、preload 与界面工程；提交依赖锁文件 |
| 界面 | React、React Router、CSS Modules | 实现首页、训练页、结果页和历史页；首版使用简单组件与样式 |
| 状态与校验 | Zustand、Zod | Zustand 保存界面状态及主进程状态快照；Zod 校验 IPC 参数、持久化输入和 AI 返回结构 |
| 本地数据 | SQLite、better-sqlite3、本地文件 | SQLite 保存结构化记录，文件保存录音；仅主进程访问数据库和文件 |
| 音频 | getUserMedia、MediaRecorder、Web Audio API | 录音、回放、相对音量采样和基础静音检测；首版只做可解释的语速、停顿、填充词与相对音量指标，不做音色、情绪或精细声学评分 |
| AI 接入 | TypeScript Provider 接口、HTTPS、协议适配器 | 语音转写可接 ASR 或多模态音频接口；转写与评价独立配置，统一结果后进入相同训练流程 |
| 测试 | Vitest、React Testing Library、Playwright | 分别覆盖状态和服务逻辑、界面交互、Electron 流程；系统能力另做真机验收 |
| 分发 | electron-builder、Windows NSIS | 生成 Windows 安装包；首版通过手动下载安装新版升级 |

实施时选择相互兼容的稳定版本，记录 Electron、Node 工具链和原生依赖版本，使用锁文件固定依赖。本文不提前承诺具体版本号；升级 Electron 时重新验证原生模块与安装包。

electron-vite 支持主进程、preload 和 renderer 的统一配置，适合这一工程结构。[官方指南](https://electron-vite.org/guide/)

## 3. 进程职责与工程组织

```text
主窗口 React ── preload 类型化接口 ──┐
                                    ├── Electron 主进程
悬浮窗 React ── preload 受限接口 ────┘       ├── 训练状态与计时
                                            ├── SQLite 与录音文件
                                            ├── AI Provider / HTTPS
                                            └── 窗口、托盘、权限与系统事件
```

主进程是训练状态的唯一权威来源，负责阶段切换、倒计时、数据读写、服务调用和窗口管理。主窗口负责页面、麦克风采集、音频回放和提醒音；悬浮窗只展示主题、阶段、倒计时，并提供暂停、继续和返回主窗口操作。

所有窗口通过 preload 暴露的有限业务接口通信，例如 `getTrainingSnapshot`、`pausePreparation`、`appendRecordingChunk`、`submitAttempt`。不向界面暴露通用 SQL、任意文件路径或原始 `ipcRenderer`。主进程对命令检查阶段、来源和参数；广播带递增版本号的完整状态快照，新窗口先拉取快照，避免两个窗口各自推进计时。

建议目录如下，业务代码与 Electron 接口保持清晰边界，但不为未来更换框架建设额外兼容层：

```text
src/
  main/          窗口、训练状态、计时、存储、AI 服务和 IPC
  preload/       主窗口与悬浮窗的最小权限桥接接口
  renderer/      页面、组件、音频采集与界面状态
  shared/        数据类型、Zod schema、错误码与默认时长
resources/
  topics.json    带稳定 ID 的精选题库
  sounds/        本地提醒音
tests/
  unit/          计时、状态、版本关系及服务重试测试
  integration/   SQLite、文件、Provider 和 IPC 测试
  e2e/           Electron 核心流程测试
docs/            产品实现与验证文档
```

SQLite 首版由主进程执行短事务，不进行长时间扫描或音频处理。若后续实测出现阻塞，再将相关工作移到 worker 或 utility process。Electron 的主进程、渲染进程与 preload 边界遵循其[进程模型](https://www.electronjs.org/docs/latest/tutorial/process-model)。

## 4. 窗口与后台运行

- 主窗口承载完整流程；悬浮窗使用独立 `BrowserWindow`，设置置顶、无边框、可拖动，显示主题、当前阶段和倒计时。位置可保存，重启时校正到当前显示器可见区域。
- 在用户开始训练时显示悬浮窗，返回主窗口不会创建第二套训练。悬浮窗不主动抢焦点；隐藏它不影响计时，并可从托盘恢复。
- 活跃训练期间，点击主窗口关闭按钮默认隐藏到托盘，并在首次发生时解释行为；录音所属窗口保持存活。显式退出应用时，提示未完成训练，停止采集并尽可能完成录音落盘后退出。
- 主进程触发阶段结束事件，主窗口播放本地提醒音；在用户开始训练的交互中初始化音频播放能力。声卡静音或系统休眠期间不承诺可听提醒，恢复后补充界面提示。
- 训练或录音期间按需关闭承载音频页面的 `backgroundThrottling`，空闲时恢复；悬浮窗只需低频刷新。倒计时正确性仍由主进程时间计算保证。
- 置顶保证范围为普通桌面应用切换；系统安全桌面和独占全屏场景不列入覆盖范围。

Electron 提供窗口置顶与后台节流配置；实际显示、提醒和后台录音效果必须在打包后的 Windows 应用中验证。[BrowserWindow 文档](https://www.electronjs.org/docs/latest/api/browser-window)

## 5. 训练状态与计时规则

准备阶段采用明确状态机，录音及 AI 处理采用独立的 attempt 状态，避免把一次转写失败误当成整轮训练失败。

| 状态 | 进入方式 | 离开方式 |
| --- | --- | --- |
| 选题 | 首页或新训练 | 锁定主题，创建训练记录并进入查资料 |
| 查资料 | 锁题后，默认 600 秒 | 到时或提前结束后进入整理 |
| 整理 | 默认 300 秒 | 到时或提前结束后进入待录音 |
| 待录音 | 准备完成或同题再讲 | 用户主动点击录音，权限与设备就绪后开始计时 |
| 录音 | 新建录音草稿，默认最多 120 秒 | 到时或主动结束后进入回放确认 |
| 回放确认 | 音频已完成落盘 | 重录、确认提交，或保留草稿稍后继续 |
| 转写与分析 | 用户确认提交后转写 | 保存原始转写，自动分析该版本并进入反馈；失败可单独重试 |
| 反馈 | 分析成功并持久化 | 查看历史、补充提纲，或创建同题的新一次演讲 |

- 查资料与整理支持暂停、继续和提前进入下一阶段；暂停不消耗剩余时长。准备完成只进入待录音，绝不自动请求麦克风或开始收音。
- 主进程使用单调时钟计算本次运行中的截止时间，定时器只负责唤醒与广播，不用每秒减一累计时间。系统时钟修改不改变剩余时长。
- 暂停保存剩余时长，恢复时重新建立截止时间；阶段切换使用状态与版本检查，防止定时器和用户点击同时触发两次切换。
- 每次状态变更持久化，运行中定期保存剩余时长快照；程序异常退出后恢复到暂停状态，由用户继续，不自动补跑阶段。快照间隔带来的恢复误差需在界面说明，首版目标控制在 5 秒以内。
- 系统休眠时暂停准备计时；恢复后等待用户继续。录音遇到休眠或设备断开时，标记中断，尝试结束并保留可播放内容，不自动续录，也不把中断内容标为完整录音。
- 系统阻塞可能延迟停止回调。120 秒是应用的停止目标，不承诺样本级精确截断；正常运行下的实际录音时长与结束延迟列入真机验收。

休眠与恢复事件通过 Electron `powerMonitor` 处理，异常关机不能依赖退出回调保存数据。[电源事件文档](https://www.electronjs.org/docs/latest/api/power-monitor)

## 6. 录音、提交与恢复

1. 用户点击录音后才申请麦克风权限，限制为音频；权限拒绝、无设备和设备占用分别显示可恢复的错误。只有采集器实际启动后才开始 120 秒计时。
2. 使用 `MediaRecorder.isTypeSupported` 选择格式，优先验证 WebM/Opus；保存实际 MIME 类型、字节数和时长。无论选择 ASR 还是多模态音频接口，都必须验证此格式以及两分钟录音的时长、大小限制；若不支持，明确提示更换配置或使用后续已实现的格式转换能力，不能只修改 MIME 声明冒充转换。首版不预装 FFmpeg。
3. 录音按块送交主进程顺序写入临时文件，携带 attempt ID 和块序号并等待写入确认，限制未确认数据量。写入失败立即提示并停止推进，不能显示“已保存”。
4. 停止后等待最后一个 `dataavailable`、`stop` 与全部写入完成，关闭文件后改为正式文件名，再将记录标为可回放。文件与数据库不能共用事务，启动时需检查并处理遗留临时文件和失配记录。
5. 检查文件非空、可解码且存在基本音量；静音检测仅用于提示，不评价声音好坏。确认提交前提供回放与重录；不将尚未确认的录音上传。
6. 重录替换的是用户明确放弃的未提交草稿；已经提交或产生反馈的演讲保留。同题再讲创建新 attempt 并沿用主题与可编辑提纲，不覆盖首次结果。
7. 发现中断临时文件时尝试恢复和回放；音频块不一定能独立播放，容器未完整结束时可能无法恢复，必须如实提示并允许重录。
8. 录音期间从同一个 `MediaStream` 分出 `MediaRecorder` 和 Web Audio 分析支路。当前代码约每 100 毫秒计算一次 RMS，用于音量条和有声标记，尚未持久化音频指标。规划中的分析模块应按音频采样时基处理连续窗口，保存 RMS、峰值和静音/VAD 区间等摘要；界面刷新定时器不作为精确停顿的采样时钟，不额外持久化原始 PCM。
9. RMS 是麦克风与系统增益共同作用下的相对振幅，不是现实世界的分贝声压。音量反馈只比较同一条录音内的片段或归一化后的趋势，使用“前后段差异较大”等表述，不直接断言“音量过小”。

录音时长使用独立计时来源，不能通过分块数量推算；`MediaRecorder` 的分块间隔并不精确。[dataavailable 文档](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/dataavailable_event)

### 6.1 演讲表现指标的计算边界

首版采用“可观察指标 + 文字教练”的组合，不让模型凭印象猜测用户的性格或情绪。指标来源和用途如下：

| 指标 | 数据来源与计算 | 首版用途与限制 |
| --- | --- | --- |
| 语速 | 当前转写版本的字符数与录音时长；有有效对齐时按分段汇总 | 字数规则排除标点和空白，说明分母是整段时长还是 VAD 有声时长；校正文字后重新计算，不伪装成专业播音评分 |
| 停顿 | 本地静音/VAD 区间；可靠转写时间戳用于关联文本位置 | 识别停顿分布并区分首尾静音，阈值可配置；分段间隔不能代表段内全部停顿，不能单凭一次停顿判断紧张 |
| 填充词、重复和改口 | 在当前转写版本上做可解释的词语和句式统计，保留原始版本供核对 | 指出“嗯、那个、然后、就是”等重复模式；校正后重新计算，不要求模型补造遗漏 |
| 相对音量变化 | Web Audio 窗口 RMS、峰值、低电平占比和前后段对比 | 说明音量是否忽高忽低或后段变小；受麦克风和系统增益影响，不输出绝对 dB |
| 音色、情绪、自信程度 | 需要额外的语音/多模态模型，结论主观且易受设备影响 | 首版不作为正式评分；以后只能作为标明“听感”的可选第二意见 |

没有转写时间戳时，仍可根据字数和录音时长计算整段语速，本地音量与静音/VAD 停顿检测也可独立运行；关闭逐词定位和依赖文本对齐的细粒度结论。`MediaRecorder` 的分块时间不能当作词语时间，提示词也不能可靠生成真实时间戳。

### 6.2 录音、可配置转写与反馈的数据流

```text
本地录音（MediaRecorder）
 ├─ 本地音频分析 → 相对音量、静音/VAD 区间等摘要 ──────────┐
 └─ 用户确认提交 → 按转写服务配置选择一个适配器             │
                   ├─ ASR 转写接口                         │
                   └─ 多模态音频接口                       │
                             ↓                             │
                  统一转写结果：逐字稿 + 可选时间戳         │
                             ↓                             │
                  保存原始版本，允许用户校正               │
                             ↓                             ↓
                  当前转写 + 主题 + 提纲 + 本地音频摘要/派生指标
                             ↓
                  按评价服务配置调用模型 → 结构化反馈
```

语音转写服务负责忠实记录原话，用户可以选择专用 ASR，也可以选择支持音频输入的大模型；两者都返回同一内部结果结构。段落级时间戳用于回放定位，词级时间戳按能力启用，时间戳缺失不阻断逐字稿保存与文本评价。

用于定位的时间戳必须来自具有明确时间对齐能力的接口字段或额外对齐模块，不通过提示词要求模型猜测。供应商字段（例如 `segments[].start/end` 或 `words[].start/end`）由适配器转换为统一单位并标注来源；多模态模型在生成文本中写出的时间不自动视为有效对齐。缺失或校验失败时明确标记并关闭相关定位能力，仍保留有效文字。

## 7. 本地数据模型与删除

数据目录使用 Electron `app.getPath('userData')` 下的独立应用目录，升级时保持应用标识与目录稳定。数据库存相对音频路径，文件名由主进程生成，界面只能传记录 ID。

| 实体 | 主要字段 | 关系与规则 |
| --- | --- | --- |
| topics | id、题目、分类、题库版本 | 训练另存题目快照，后续改题库不改变历史 |
| training_sessions | id、主题快照、提纲、阶段、剩余时长、创建时间 | 一次锁题创建一条；保留当前准备状态与提纲 |
| attempts | id、session_id、序号、提纲快照、音频路径、MIME、时长、状态、音频摘要 JSON 与算法版本 | 同题多次演讲分别保存；每次演讲使用自己的提纲快照；相对音量、VAD 区间等仅依赖录音的摘要在校正转写时复用 |
| transcript_revisions | id、attempt_id、版本、文本、来源、转写服务/模型/适配器版本、可选分段与词级时间戳、对齐状态、创建时间 | ASR 或多模态模型产生的原始转写不可覆盖；校正产生新版本，旧时间戳不自动成为修改后文字的有效对齐 |
| feedback_runs | id、attempt_id、transcript_revision_id、结果 JSON、评价服务/模型/适配器与提示词版本、音频摘要版本、状态 | 每条反馈关联转写和指标版本；字数、语速、填充词等派生指标随转写版本计算 |
| service_jobs | id、attempt_id、类型、输入版本、请求标识、状态、错误码 | 保存转写与分析的任务状态，用于重试与恢复 |
| local_events | id、事件类型、session_id、attempt_id、耗时、时间 | 只记最少的本地效果事件，不包含正文与音频；删除训练时清理其关联事件 |

使用外键、短事务和 schema 版本迁移。提纲防抖保存，切换阶段前等待保存确认；提交演讲时固定一份提纲快照。相同输入的处理中任务复用请求标识，防止连续点击重复发起。

服务配置分为 `transcription` 和 `feedback` 两组，连接设置及密钥引用由主进程管理。每个阶段发起请求时固定其服务、模型和适配器版本，处理中修改设置不改变在途请求或历史结果；重试明确显示实际接收方。密钥不写入转写、反馈或任务快照。

删除整条训练包括其所有 attempts、录音和临时文件、转写版本、反馈、任务记录及关联事件。先标记删除并取消任务、停止回放，再按记录定位文件进行清理，最后删除数据库关系；中途失败保留待清理状态供下次启动重试。迟到的网络响应先检查删除标记与输入版本，不得重新生成已删除记录。

这里的删除指清除本应用管理的数据，不承诺磁盘取证意义的安全擦除，也不代表第三方已删除留存。数据库迁移前可建立临时备份，成功后立即清理，失败时只用于恢复；常规历史删除不能遗留应用自行保管的旧备份副本。

## 8. AI 服务与反馈流程

采用“可配置转写 + 本地音频指标 + 独立评价”的分层方案：

- **语音转写服务**：按用户配置调用专用 ASR 或支持音频输入的大模型，返回忠实逐字稿和可选时间戳。原始转写保存后不可被润色稿或评价覆盖；多模态模型是正式可选的转写实现。
- **本地音频与文本指标模块**：从录音提取峰值、相对音量和静音/VAD 区间，从当前转写计算字数、语速、填充词和重复模式。可靠时间戳用于关联文本与录音片段；缺失时关闭相关细粒度结论。
- **演讲评价服务**：按独立配置的模型，根据主题、提纲、指定版本的转写和指标生成教练反馈。默认输入是文字和指标，不要求评价模型能接收音频。

`TranscriptionProvider.transcribe` 和 `FeedbackProvider.analyze` 保持独立，界面只调用业务命令，不直接连接供应商。同一个模型可以分别执行转写和评价，但始终分两次调用、保存两个阶段的结果，支持校正后仅重新评价。整体听感的音频评价属于额外可选任务，与选择多模态模型做转写是两项独立能力，不覆盖逐字稿、时间戳或结构化指标。

### 8.1 转写与评价的独立配置

| 设置分组 | 配置字段 | 连接与模型规则 |
| --- | --- | --- |
| 语音转写服务 `transcription` | 服务商预设、接口适配器 `adapterId`、HTTPS API 地址 `baseUrl`、密钥引用 `credentialRef`、模型 `model`、接收方与留存说明 | 必须支持音频输入；可选 ASR 或多模态音频接口；普通文本模型或只支持图像的模型不能直接转写录音 |
| 演讲评价服务 `feedback` | 独立的服务商预设、`adapterId`、`baseUrl`、`credentialRef`、`model`、接收方与留存说明 | 必须支持文字分析和可校验的结构化反馈；可以与转写使用不同服务商、地址、密钥和模型 |
| 复用连接 `reuseTranscriptionConnection` | “使用与转写相同的连接”开关 | 仅复用地址、密钥引用和接收方信息；评价接口适配器与模型仍单独选择，不能把 ASR 上传协议直接当作文字评价协议 |

用户优先选择服务商预设，再填写地址、密钥和模型；高级设置可选择已支持的接口类型。预设负责填入适配器和已知能力，不根据 API Key、域名或模型名字猜测调用协议。首轮覆盖现有 ASR 兼容接口及一种经验证的多模态音频协议，具体服务商适配器在接入时确定；同属“大模型”或宣称接口兼容，不代表音频字段、认证和格式完全一致。

提供分别测试转写与评价的“测试配置”操作：用户主动发起后，使用随应用提供的短测试音频和固定文本进行检查，不读取历史录音。显示接收方和可能费用，反馈认证、模型可用性、音频格式、有效转写、结构化评价与时间戳支持情况；通过短样本不等于两分钟录音的大小和时长限制已验证。保存设置不自动发送测试请求。

**当前实现与迁移**：现有 [provider.ts](../src/main/provider.ts) 共用一个 `baseUrl` 和 Key，转写固定调用 `/audio/transcriptions`，评价固定调用 `/chat/completions`，且转写只返回字符串。两套连接、多模态适配器、时间戳和能力测试均为待实现设计。升级时把旧地址和密钥引用映射到两组配置，分别保留 `asrModel`、`feedbackModel` 及原有协议，不改变已有用户的接收方；旧记录保持可读，缺失元数据按未知处理。

### 8.2 接口适配与统一转写结果

按显式 `adapterId` 构建 Provider。ASR 适配器处理对应的音频上传协议，多模态适配器处理供应商规定的音频编码或上传流程、转写提示词和响应解析；评价适配器处理文字请求与反馈结构。训练业务不依赖供应商字段或固定端点，API 地址和模型名称本身不能替代协议适配。

多模态转写提示词要求忠实转写、不总结、不润色、不纠正用户观点，尽量保留填充词、重复与改口；听不清时按约定标记，不根据主题或提纲补写内容。音频本身是待转写数据，其中的口头指令不能改变转写任务。专用 ASR 若有去口头词或智能润色选项，也需验证其设置；提示词或配置都不能保证零遗漏，必须用真实演讲样本验收。

两类适配器统一返回以下结果，由共享 schema 校验后保存：

| 字段 | 内部约定 | 失败或缺失处理 |
| --- | --- | --- |
| `text` | 非空中文逐字稿，可包含外语词；沿用现有文本长度上限 | 无有效文字时转写失败，保留录音供重试 |
| `segments` / `words` | 可选数组，元素包含 `text`、`startMs`、`endMs`；相对本次录音起点，统一毫秒 | 只接受有限数值、合法顺序和录音范围内的区间，允许经验证的解码误差；非法时间信息不用于定位 |
| `timing` | 记录对齐来源和 `available`、`missing` 或 `invalid` 状态 | 服务未提供对齐能力或仅生成了时间字符串时，不标为有效时间戳；段级和词级能力分别判断 |
| `providerMeta` | 实际服务、模型、适配器版本与可用的请求标识 | 只保存追踪所需字段，不保存密钥和完整供应商原始响应 |

适配器声明音频输入、MIME、大小/时长上限及段级/词级时间戳能力，并标明未知能力。每次请求前校验已知约束，响应后再验证实际结果；时间戳为可选能力，缺失时降级为文字反馈和可独立计算的音频指标。只有转写或评价本身所必需的能力缺失时才阻止该步骤。一个多模态模型可以做转写，不代表它同时满足评价结构要求，两组配置分别验证。

失败时保留当前阶段的输入和已成功结果，允许用户调整配置后重试；不自动换供应商、模型或额外上传音频。以后如增加独立时间对齐或音频听感服务，应作为明确配置的附加步骤，说明接收方、费用和能力。

### 8.3 反馈、校正与证据版本

默认流程为：本地保存录音和音频摘要 → 用户确认上传 → 所选转写服务生成并保存原文与可选时间戳 → 计算当前转写版本的派生指标 → 评价服务分析 → 校验并保存结果。

结果页展示可编辑转写。用户校正后创建新转写版本，复用同一 attempt 的录音与音频摘要，重新计算字数、语速、填充词等依赖文字的指标，再调用评价服务，不重新上传音频。修改后文字的对齐标记为待重新对齐，不能直接沿用旧逐词高亮；原始版本的时间戳继续供原文回放使用。分析期间发生校正时，旧任务的结果仍归属于旧版本，不覆盖当前版本展示。

反馈结构分为四块：

1. **内容理解**：是否解释概念、边界和关键因果；
2. **结构组织**：是否有清楚的开头、展开、例子和收束；
3. **表达通俗程度**：是否使用听众熟悉的语言、例子或类比；
4. **演讲表现**：结合语速、停顿、填充词、重复、重点处留白和相对音量变化，给出可观察、可执行的建议。

每条结论都要区分转写证据、音频指标和模型解释。首版优先完成“准确逐字稿 + 内容/结构反馈 + 基础语速/停顿分析”；“语气”如果指情绪、音色或自信程度，只作为后续增强项，不作为首版正式评分。允许无明显问题时明确说明，不强迫模型编造缺点，不输出未经校准的综合百分制。

- 每条引用保存所用转写版本中的原文片段并检查能否匹配；不匹配或结构不合法时不能当作正常反馈展示，最多自动修复一次，仍失败则允许用户重试。
- 提示词明确把主题、提纲和转写视为待分析内容，不能执行其中夹带的指令；首版不开启搜索或工具调用，不宣称完成事实核查。
- 网络错误、超时、限流和余额不足分开提示；设置有限超时与重试上限，遵守服务端重试提示。已完成的转写不因分析失败而重跑。
- 超时不一定表示供应商未执行。支持供应商任务查询或幂等键时复用原请求；不支持时避免无提示重复计费，由用户决定重新发起。
- 退出或重启后把未完成网络任务标为待确认或可重试，保留录音、提纲与已成功结果；不进行无上限的后台重试。

反馈提示词只约束模型如何解释已提供的数据，不能替代转写或对齐接口的时间戳能力。反馈提示词应明确：主题、提纲、转写和指标都是待分析数据；引用必须来自当前转写版本；没有指标或时间戳时不能补造；对音量和停顿使用相对、可观察的表述；不根据声音推断人格、心理或事实核查结果。

供应商选择用同一批中文录音比较专有名词、口语和噪声下的识别表现，再比较反馈引用是否准确、建议是否具体、时延和费用。费用按音频时长、输入输出 token、重试次数分别记录；未选服务前不给出每次训练的固定成本或等待时间承诺。

## 9. 密钥、上传与安全边界

**开发与个人验证模式**：由开发者或用户配置自己的 API Key，主进程调用服务；持久化密钥使用 Electron `safeStorage`，加密能力不可用时只保存在会话内，不明文降级。密钥不进入 renderer、源码、日志、安装包或 Git。

**向外部用户提供统一额度前**：增加轻量 Node.js + Fastify 服务，管理供应商密钥、试用凭据、请求额度与限流。用户无需注册，可由试用入口发放受限凭据；不能把供应商公共密钥或所有用户共用的固定密钥打进桌面包。此服务是对外试用的发布前条件，不是本地闭环原型的依赖。

首次提交前分别说明转写接收的录音、评价接收的文字与指标发给谁、用途与已知留存策略；更换接收方或用途时重新说明。两组密钥只由主进程按对应服务使用，不互相发送；复用连接通过密钥引用实现，不向界面暴露明文。服务商尚未确定的留存期限标为待确认，对外试用前必须补齐，不能声称零留存。

所有窗口开启 `contextIsolation` 与 `sandbox`，关闭 `nodeIntegration`。生产界面通过受限的本地自定义协议加载，配置 CSP；只允许明确的本地资源映射，拒绝路径穿越。音频按记录 ID 映射并支持回放所需的范围读取。

同时设置权限检查与权限请求处理器，仅允许可信主窗口在用户发起录音后请求音频权限；悬浮窗不授予麦克风权限。校验每个 IPC 的发送窗口、frame、来源与数据。外链仅允许明确的 HTTP/HTTPS 地址交给系统浏览器打开，阻止应用内任意导航和新窗口。模型结果按文本渲染，不执行 HTML。

这些边界依据 Electron 的[安全建议](https://www.electronjs.org/docs/latest/tutorial/security)、[权限接口](https://www.electronjs.org/docs/latest/api/session)和[密钥存储接口](https://www.electronjs.org/docs/latest/api/safe-storage)。

## 10. 性能与分发

首版优先保证训练可靠，避免引入本地模型、大型动画资源和常驻后台轮询。仅保留主窗口与必要的悬浮窗；页面离开后释放回放资源，结束录音后停止所有麦克风 track，空闲时停止音量检测。

之前讨论的安装包 100～200 MB、安装占用 300～600 MB、运行内存 200～400 MB 均为粗略规划值，**不是验收承诺或实测结果**。首个可运行版本记录安装包大小、安装后空间、冷启动耗时，以及空闲、悬浮计时、录音和分析时的全部应用进程内存与 CPU；说明测试机器、系统版本和应用版本后再设预算。

本地录音按需保留，历史页显示磁盘占用并允许删除，不默认无限期向服务器备份。只有结构化元数据进入 SQLite，不把音频放进数据库。

better-sqlite3 是原生模块，安装、升级 Electron 和打包时必须针对目标 Electron ABI 与架构重建，并在安装包中检查原生文件的加载方式；开发环境能运行不能代替安装包验证。[原生模块指南](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules)

使用 electron-builder 生成 NSIS 安装包。内部验证包可以先用于受控测试，面向外部用户分发前落实 Windows 代码签名；代码签名不等于保证没有系统信誉提示。首版手动更新，覆盖安装必须保留 userData；数据库升级前验证备份与恢复，回滚程序时不能直接打开不兼容的新 schema。[electron-builder 文档](https://www.electron.build/)

## 12. 开发顺序与当前就绪程度

1. **桌面基础验证**：搭建 Electron 工程，验证独立悬浮窗、后台计时提醒、麦克风权限、两分钟录音、SQLite 原生模块和 Windows 安装包。先实测体积与内存。
2. **本地训练闭环**：实现题库、准备状态机、提纲保存、录音确认、历史与删除；用假 Provider 打通页面与数据流程。
3. **AI 接入与复盘**：实现两组服务配置、旧配置迁移、ASR 与多模态音频适配器、统一转写结果和配置测试；接入可选时间戳、基础音频指标、校正、多版本反馈和同题重讲，补齐重试、费用与留存说明。
4. **外部试用准备**：按分发范围落实服务端密钥保护、额度、代码签名、升级与回滚验证，完成真机验收后再提供安装包。

当前已有本地训练 MVP，下一步按本方案扩展可配置转写与评价服务。Windows 首发范围是本方案的实施假设；具体适配器、外部试用方式与留存策略必须在对应阶段结束前确定。以上阶段用于控制依赖，不构成交付日期或性能保证。
